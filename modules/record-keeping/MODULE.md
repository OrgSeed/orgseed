# Module: record-keeping

**For.** A fuller journal of what the organization does: an event for every kind of activity, not only the ones the core asks for.

**Adds.** All event types in `records/events.jsonl` (`schemas/event.schema.json`), at the time they happen.

**Always kept, whatever modules are on (core).** The witnessed git history, written only by the founder's close-out; proposals, decisions and the founder's signatures, including declined and open proposals; what was turned back (`records/declines.jsonl`); claims (`records/claims.jsonl`); drills; session start and end; structural changes; record corrections. This basic record is the same in every configuration, so switching this module on or off never changes how the basic record is kept, and organizations or versions of one organization can be compared on it.

**Works with.** Every module. Its rules ask members to record what happened, not to apply a standard, so it refers to no other module's rules. Modules with their own ledgers (corrections, commitments, recall, dissent, reviews, needs) keep them whether or not this module is on.

**Costs.** A line per event. Members' lines are their own account; how complete they are can differ between members and models, and is worth checking against the witnessed history and, where one exists, an independent capture (`docs/RECORDS.md`, "Who writes what").

## Rules

### REC-1 Record each event as it happens
rule: Append an event for each piece of work finished, each redirect, each claim recorded, each check run, each tool action, each recall check, each change of member or model, each dissent and each hand-back, when it happens.
why: a journal written at the moment is more complete and less shaped by hindsight than one put together at the end.

### REC-2 Record, do not evaluate
rule: In the journal, describe what happened in plain terms. Leave judgments of quality to decisions, reviews and corrections.
why: a journal that mixes events with verdicts is harder to compare across organizations and members.

## Grounding

**On the literature.** This module, like the record-keeping core, is built on method; no theory of conduct is claimed. The closest line we have read is Simon's, about design processes written as computer programs: "Whatever judgment or experience was used in creating the programs must now be incorporated in them and hence be observable" (Simon 1996, p. 135; read). His point concerns a design set down in code, as the seed's own files are. It says nothing about a record of what members did.

**What this design expects.** [ours] No effect on how members act. The record matters because every other expectation is read off it: one record, kept one way whatever the configuration, beyond any member's reach (`docs/RECORDS.md`).

**The other side.** The record shows what was done, not the reasons for it, and the lines members write are their own account of it (`docs/RECORDS.md`, "Who writes what").
